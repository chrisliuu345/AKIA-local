## 1. 发现并修复的缺陷

### 1.1 功能级（接线落空与错算）

| 缺陷 | 现象/证据 | 影响 | 修复 |
|------|-----------|------|------|
| 共享保存必然失败 | `ui/main_window._on_save_shared` 传 `evidence_events=self.ledger`，而 `SharedProjectManager.save_shared` 无此形参 → `TypeError`，被宽异常吞成"保存失败"弹窗 | 「文件 → 保存到共享目录」永远失败（案例/标准/测量/账本全部无法共享） | `save_shared` 增加 `evidence_events` 并透传；`tests/test_ledger_wiring.py` 新增菜单动作端到端回归（含错误弹窗熔断） |
| 配对检验错配 | 两列各自 `dropna()` 后按位对齐，两列缺失位置不同时配错行 | 案例工作台「配对检验」在含缺失数据时结论不可信 | 改为成对剔除（任一侧缺失整行剔除）；新增缺失位置不同的回归用例 |
| 案例号同秒撞号 | `CASE-YYYYMMDD-HHMMSS` 无随机后缀，同秒连续创建出重复 ID | 案例中心/账本 `case:<id>` 引用混叠 | 案例号 = 本地时区时间 + 4 位随机后缀；纳入时间守卫模块清单 |

### 1.2 数据完整性

| 缺陷 | 现象/证据 | 影响 | 修复 |
|------|-----------|------|------|
| 尾行恢复误删合法数据 | 账本/测量 JSONL"无尾随换行"即判定截断并丢弃尾行，`load_file` 还会把瘦身后的文件写回 | 完整但缺尾随换行的文件（外部产出/编辑）静默丢最后一条事件 | 仅当尾行 JSON 解析失败才判定截断；完整文件不改写；两处各补回归 |
| 标准注册表追加非原子 | 追加失败先改 `previous.valid_to` 再校验（如重复 ID）→ 旧版本已关闭、新版本未加入 | 失败一次等于丢"现行标准"（`current()` 为空） | 全部校验先于状态变更（`replaces` 预演），失败保持原状 |
| 乱序时间列被拒 | `from_dataframe` 取首/末行时间，乱序导出文件触发 `ts_end < ts_start` 拒绝 | 真实乱序报表无法生成测量事件 | 改为全窗口 `min/max`；补乱序回归 |

### 1.3 性能与稳定性

| 缺陷 | 现象/证据 | 影响 | 修复 |
|------|-----------|------|------|
| 泄漏扫描 O(候选 × 文件) | 2 万行唯一值表实测 **263.57s**（同步阻塞 UI；百万行不可用） | 「导出脱敏分享包」实际不可用 | 数值候选单遍 token 提取（全量、等价数字边界）；文本候选全量 token + 小文件子串（≤1MB / 前 2000 候选）+ 单列候选上限；结果附 `candidates_*` / `large_files_token_only` / `capped` 元数据；实测 **0.43s**（约 600×） |
| 插件超时线程阻塞退出 | 数据源插件挂死时 `ThreadPoolExecutor` 工作线程在解释器退出被 join | 程序关不掉（需强杀） | 改守护线程 + Event 等待；超时/异常语义不变 |
| 证据视图全量重算 | 每次切换结论都重跑 `ledger.verify()` | 大账本（数万事件）界面卡顿 | 会话内缓存链校验结果，按钮可手动重算 |
| 凭证包校验脆弱 | manifest 结构异常（`files` 非映射）抛 `AttributeError` 逃逸 | 独立校验入口崩溃而非返回结构化错误 | 扩大捕获返回 `ok=False + problems` |

### 1.4 可观测性与语义

- `_ledger_failures` 语义混叠：加载期解析错误被计入"写入失败累计"→ 现只统计本会话追加
  失败；加载错误经 `verify()` 链校验 + 状态栏提示浮出，不再只进日志。
- 账本/测量事件导出对非 dict `case` 载荷做防御归一化（`evidence_pack`）。

## 4. 对 v4.4.0 的准备建议

1. **接线完整性制度化**：本次两个功能级缺陷（共享保存、配对错配）都属于"菜单动作
   端到端无人跑"的盲区——现有 2194 例测试无一覆盖 `_on_save_shared` 主路径。
   建议 v4.4.0 收口批次增加"主窗口动作离屏冒烟"清单（所有菜单动作至少一次真实命中）。
2. **可信抽样直接复用本轮基建**：确定性（`valid_from` 单调 + 原子注册表）、
   留痕（账本事件 + 指纹）、有界扫描（含元数据）的修复模式均按 v4.4 B3 的
   "转移状态机 + 抽样决定入账本"目标设计，可直接延用。
3. **补丁与版本**：本审查修复不改变 schema/API/`.qap` 版本；建议作为 v4.3.1 源码补丁
   单独交付（与 v4.2.1 先例一致），或并入 v4.4.0 首批提交。
