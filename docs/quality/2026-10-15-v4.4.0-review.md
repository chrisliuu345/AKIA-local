### 1.1 [发布阻断] 打包产物缺失全部 Tab 与连接器插件

| 项 | 内容 |
|----|------|
| 现象/证据 | PyInstaller 归档清单（v4.2.0 / v4.3.0 / v4.4.0 AppImage 与 `build/AKIA.dist/AKIA.exe` 四份实测）：`ui.tabs`、`chart_tab`、`connectors.plugins` 命中均为 **0**，而对照模块 `analysis.time_series.arima` 命中 1；`build/pyi_work/AKIA/PYZ-00.toc` 同样为 0。修复前用 `tools/verify_bundle.py` 核验 Windows 构建列出 **44 个缺失模块**。 |
| 机制 | `ui/main_window.py:1661` 懒加载 `importlib.import_module(module_path)` 与 `connectors/registry.py:35` 的 `f"connectors.plugins.{stem}"` 均为动态导入，PyInstaller 只跟踪字面量 import；`build_pyinstaller.py` 未做子模块收集（v4.2.0 起 Tab 懒加载后长期存在）。 |
| 影响 | 打包版所有 Tab 不可用（弹"缺少运行依赖: ui，pip install -r requirements.txt"误导提示）、连接器插件（串口/CMM/Modbus/OPC-UA/MQTT）不可用；已发布的 3 个 AppImage 与今日 Windows 包均受影响。 |
| 修复 | ①`build_pyinstaller.py` 新增 `COLLECT_SUBMODULES = ["ui.tabs", "connectors.plugins"]` 并接线 `--collect-submodules`；②新增 `tools/verify_bundle.py`（读取 CArchive+PYZ，核对注册表全部 Tab 模块与插件模块），构建收尾自动执行、缺失即中止；③`connectors/plugins/__init__.py` 增 `PLUGIN_MODULES` 静态清单，`connectors/registry.py` 冻结环境（源码目录不可扫描）回退该清单——否则即便模块在包内，插件发现仍为空；④`tests/test_bundle_manifest.py` 棘轮（构建脚本接线、清单与目录零漂移、注册表模块可解析）。 |
| 验证 | 重新构建 Linux onedir 后：`verify_bundle` 输出 `[ok] akia: 44 个动态导入模块全部在包内（共 5128 个冻结模块）`；归档内 `ui.tabs.*` / `connectors.plugins.*` 全部命中。 |

### 1.2 [功能级] 项目载入后立案编排器持有旧 context/ledger

| 项 | 内容 |
|----|------|
| 现象/证据 | 载入 `.qap` 后触发 critical 告警的探针实测：活动 `project_context.eight_d_reports` 为 0，旧（被替换）context 为 1；`open_eight_d_report()` 返回 False；`alert_case_opened` 事件落在旧账本对象（不计入活动账本、不落盘）。 |
| 机制 | `_apply_loaded_project` 会**替换** `self.project_context`（`PC.from_dict`）与 `self.ledger`（`_restore_ledger`），而 `AlertCaseOrchestrator` 在 `__init__` 固定持有二者的旧引用且从未重绑（`ui/main_window.py`）。 |
| 影响 | 载入项目（最常见的现场路径）后：自动立案的 8D 草稿不落盘、8D Tab / 案例双向定位失效、D2 快照丢失特性/FMEA 上下文证据、证据账本缺 `alert_case_opened`。 |
| 修复 | `_apply_loaded_project` 恢复账本后显式重绑：`alert_case_orchestrator.context = self.project_context; .ledger = self.ledger`（先于 `_restore_case_workflows` 中的会话重建）。 |
| 回归 | `tests/test_alert_case_ui.py::TestProjectLoadRebind`（保存→载入→告警→断言草稿在活动上下文、可打开、事件在活动账本）。 |

### 1.3 [数据丢失] 控制计划节流窗口内保存丢最后一笔编辑

| 项 | 内容 |
|----|------|
| 现象/证据 | 探针：编辑单元格后立即序列化（即保存路径写入的内容）仍为旧值 `10±0.05mm`；`_flush_pending_sync()` 后才变 `10±0.02mm`。 |
| 机制 | B7-3 引入 1.5s 节流（`_schedule_sync` 定时合并）；`_on_save_project` / `_on_save_shared` 直接序列化 `project_context.to_dict()`，未冲刷挂起编辑。 |
| 影响 | 「编辑后立即保存工程/保存到共享目录」静默丢失最后一笔控制计划编辑（保存的是旧版本）；关闭程序同理不落库。 |
| 修复 | `ControlPlanTab.flush_pending_edits()`（公开冲刷入口）+ `MainWindow._flush_tab_edits()`（保存/共享保存前对已加载 Tab 统一调用，单项失败不阻断保存）。 |
| 回归 | `tests/test_standard_wiring.py::TestControlPlanSaveFlush`（编辑→立即保存→重载 .qap 断言新值已落盘；并断言保存前存在挂起状态）。 |

### 1.4 [安全] Gemini 协议 API key 移出 URL

| 项 | 内容 |
|----|------|
| 现象/证据 | `core/llm_client.py` 的 `_gen_gemini` 流式请求 `?alt=sse&key=<api_key>` 与 `test_connection` 的 `/models?key=<api_key>`；密钥会进入代理/网关/服务端访问日志（错误消息与日志本身已掩码）。 |

| 回归 | `tests/test_llm_client_protocols.py` 两处更新：断言 URL 无 `key=`、请求头携带密钥。 |

### 4.2 兼容与文档

- **旧版本打开新版 `.qap`**：证据事件类型为闭集校验，v4.3.x 读取 v4.4.0 新增的 7 类
  事件（`sampling_plan_selected` 等）会判为解析错误并跳过，账本链校验随之失败
  （仅警告，不阻断打开）。建议迁移手册补充"升级后的项目勿用旧版本回写"，或后续
  在账本读取层引入未知类型宽容模式。
- `.qap` 2.0 反向兼容（旧版忽略新四段）与 1.6–1.9 只读兼容实测成立；`.qap` 往返
  （含四新段）回归通过。
- 归档读取（证据包 / 分享包 / `.qap`）无 zip 条目/总量上限（无 zip-slip；可内存
  DoS）——与 v4.3.0 审查结论一致，建议在 v4.5 CLI/SDK 对外暴露前加限。

### 4.3 观察项（记录，不阻断）

- `AlertCaseOrchestrator.rebuild()` 返回计数按"链接数"累加，文档写"会话数"（当前调用方未使用返回值）。
- `core/sampling_note.thin_indices` 的 `kept_count` 在多个 keep 目标映射到同一槽位时会计满、
  与实际保留数略有出入（界面措辞"强制保留 N 点"可能高估）；判异点通常稀疏，影响低。
- `core/alert_case.py` 未纳入时间守卫模块清单（当前实现均正确使用 `astimezone`）。
- 插件在进程内以完整用户权限执行、告警联动可执行配置命令（默认关闭）——属架构固有，
  建议在文档中明示信任模型（"插件 = 完全信任代码"）。
- `MSA_D2_STAR` 表外 n 的近似回退公式建议在公式线复核时与 AIAG 表外定义核对。
